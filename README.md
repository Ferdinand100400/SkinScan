# Skin Scan — Backend

## 1. О проекте

**Краткое описание:**  
Серверная часть приложения для скрининга кожи с использованием компьютерного зрения. 
На текущий момент реализован базовый каркас системы: 
аутентификация пользователей, управление сессиями через JWT, хранение учётных записей в PostgreSQL и система централизованной обработки ошибок. Ядро продукта — загрузка и анализ фотографий родинок — находится в активной разработке.

**Текущий статус:**
- ✅ Регистрация новых пользователей с хэшированием паролей (BCrypt).
- ✅ JWT-аутентификация (с access и refresh токенами).
- ✅ Глобальный обработчик исключений с единым форматом ошибок.
- ✅ Эндпоинт `/check-run` с проверкой связности с БД.
- ✅ Эндпоинты регистрации, авторизации и изменения данных пользователя.
- ✅ Ограничение на кол-во авторизаций и регистраций с одного IP
- ✅ Миграционная схема для таблиц (Liquibase).
- ✅ Многопрофильная конфигурация (local, dev, prod).
- ✅ Загрузка и анализ фотографий реализованы (асинхронная обработка, хранение файлов, статусная модель).
- ✅ Фоновый процесс по обработки зависших фотографий, если статус фотографии долго в обработке 
- ⚠️ ML-компонент пока работает в режиме заглушки, возвращающей тестовые данные.

## 2. Стек технологий

**Описание выбранных решений с обоснованием:**

- **Язык:** Java 21.
- **Фреймворк:** Spring Boot 3.x. Используется как стандарт де-факто для RESTful сервисов; предоставляет встроенный контейнер сервлетов (Tomcat) и гибкую систему конфигурации.
- **База данных:** PostgreSQL 18+. Реляционная СУБД выбрана для гарантированной целостности данных (внешние ключи, транзакции) и поддержки JSONB-полей, которые понадобятся для хранения результатов ML-анализов.
- **Миграции:** Liquibase. Позволяет версионировать изменения схемы БД.
- **Безопасность:** Spring Security + JWT. Токены хранятся в памяти сервера (без Redis) на данный момент, что допустимо для MVP.
- **Сборка:** Gradle (Kotlin).
- **Документация API:** OpenAPI 3 (Swagger) с автоматической генерацией через Springdoc. Доступна по адресу `/swagger-ui.html`или по эндпоинту `/docs`.

## 4. Настройка и запуск (локальная разработка)

### 4.1 Клонирование репозитория
```bash
git clone <url-репозитория>
```

### 4.2 Настройка базы данных
Создайте базу данных в PostgreSQL:
```sql
CREATE DATABASE skinScan_db;
CREATE USER skinScan_user WITH PASSWORD 'your_strong_password';
GRANT ALL PRIVILEGES ON DATABASE skinScan_db TO skinScan_user;
```

### 4.3 Конфигурация приложения

Приложение автоматически использует **профиль `local`**
### 4.4 Запуск приложения
Через Gradle:
```bash
./gradlew bootRun
```
После запуска сервер будет доступен по адресу: `http://localhost:8080`.

### Для генерации секрета на базе HS256
```bash
openssl rand -base64 32 
```

### Запуск с хранением в оперативной памяти приложения
```bash
export JWT_SECRET=your-super-secret-key-at-least-32-characters-long
./gradlew bootRun --args='--spring.profiles.active=local'
```

### Запуск с хранением в БД (Postgres) и использованием `minio`

Для запуска MinIO через Docker, необходимо запустить в докере MinIO
```bash
docker-compose up -d
```
И запустить приложение с профилем `minio`.
```bash
export JWT_SECRET=your-super-secret-key-at-least-32-characters-long
./gradlew bootRun --args='--spring.profiles.active=minio'
```
Для остановки и удаления контейнера:
```bash
docker rm -f minio
```

### Проверка успешности:
- Запрос `GET /skinScan/check-run` должен вернуть статус, время запроса, текущее время и запуска приложения.
- Swagger-документация доступна: `http://localhost:8080/swagger-ui.html`.

## 5. API Документация (Текущие эндпоинты)

Все эндпоинты документированы через OpenAPI. Интерактивная документация доступна после запуска по адресу `/swagger-ui.html`. Ниже описаны ключевые эндпоинты.

### 5.1 Регистрация пользователя
- **Метод:** `POST /skinScan/register`
- **Тело запроса (JSON):**
    - `login` (string, обязательное).
    - `password` (string, обязательное) — минимум 6 символов.
    - `email` (string) — должен быть корректным email-адресом.
    - `phone` (string).
- **Успешный ответ:** `201 Created` с телом:
    - `userId` (UUID) — идентификатор созданного пользователя.
- **Ошибки:**
    - `400 Bad Request` — невалидный email или пароль.
    - `409 Conflict` — пользователь с таким email уже существует.

### 5.2 Аутентификация (Логин)
- **Метод:** `POST /skinScan/login`
- **Тело запроса:** 
  - `login` (string).
  - `password` (string).
- **Успешный ответ:** `200 OK` с телом:
    - `type` тип авторизации пользователя.
    - `accessToken` пользователя.
    - `refreshToken` пользователя.
- **Ошибки:** `401 Unauthorized` — неверные учётные данные.

### 5.3 Обновление Access токена
- **Метод:** `POST /skinScan/refresh-token/access`
- **Тело запроса:**
  - `refreshToken` (string) - текущий refresh токен.
- **Успешный ответ:** `200 OK` с телом:
  - `type` тип авторизации пользователя.
  - `accessToken` новый access токен пользователя.
  - `refreshToken` новый refresh токен пользователя.
- **Ошибки:** `401 Unauthorized` — неверный или истекший refresh токен или пользователя не существует.

### 5.4 Обновление Refresh токена
- **Метод:** `POST /skinScan/refresh-token/refresh`
- **Тело запроса:**
  - `refreshToken` (string) - текущий refresh токен.
- **Успешный ответ:** `200 OK` с телом:
  - `type` тип авторизации пользователя.
  - `accessToken` новый access токен пользователя.
  - `refreshToken` новый refresh токен пользователя.
- **Ошибки:** `401 Unauthorized` — неверный или истекший refresh токен или пользователя не существует.

### 5.5 Проверка состояния сервера
- **Метод:** `GET /skinScan/check-run`
- **Ответ:** `200 OK` с JSON:
    - `статус` — `Успешно` или `Ошибка`.
    - `БД` — `Postgres`.
    - `Результат работы БД` — `1` если успешно или `0` если ошибка соединения с БД.
    - `Время запроса, мс` — время выполнения запроса в мс.
    - `Текущее время`.
    - `Время старта приложения`.

### 5.6 Обновление данных пользователя
- **Метод:** `PUT /skinScan/user/update`
- **Заголовок:** `Authorization: Bearer <AccessToken>`
- **Тело запроса (JSON):**
  - `login` (string, обязательное).
  - `password` (string, обязательное) — минимум 6 символов.
  - `email` (string) — должен быть корректным email-адресом.
  - `phone` (string).
- **Ответ:** `201 OK` с полем: `id`.
- **Ошибки:**
  - `400 Bad Request` — невалидный email или логин.
  - `401 Unauthorized` — неверный или истекший токен.

### 5.7 Смена пароля пользователя
- **Метод:** `PUT /skinScan/user/update/{login}`
- **Заголовок:** `Authorization: Bearer <AccessToken>`
- **Тело запроса (JSON):**
  - `newPassword` (string, обязательное).
  - `oldPassword` (string, обязательное).
- **Ответ:** `201 OK` с полем: `id`.
- **Ошибки:**
  - `400 Bad Request` — невалидный новый пароль.
  - `401 Unauthorized` — неверный или истекший токен.

### 5.8 Загрузка фотографии
- **Метод:** `POST /skinScan/photos/upload`
- **Заголовок:** `Authorization: Bearer <AccessToken>`
- **Тело запроса (JSON):**
    - `file` (MultipartFile, обязательное).
    - `tags` (string[]).
    - `description` (string) — ограничение по длине.
    - `category` (string).
- **Ответ:** 
  - `202 Accepted` с полем: `id` — добавлена фотография.
  - `200 Ok` — фото с таким именем уже существует.
- **Ошибки:**
    - `400 Bad Request` — Ошибка валидации, а также неверный формат фотографии или превышен размер файла.
    - `401 Unauthorized` — Необходима аутентификация, неверный или истекший токен.
    - `500 Internal Server Error` — Ошибка добавления файла на стороне файловой системы.
- Файл сохраняется в хранилище (локальная файловая система или MinIO - выбор через профили). 
Структура папок: {base_dir}/{userId_short}/{year}/{month}/{uuid}.{mimeType}
- **Фоновый асинхронный процесс:**
После сохранения метаданных фото со статусом `Загружено` в БД запускается асинхронный процесс:
  - Запускается анализ (сейчас заглушка, эмулирующая работу ML).
  - После завершения результат сохраняется в таблицу analyses со статусом `Анализ завершен`.

### 5.9 Получение всех фотографий
Получение метаданных всех фотографий, которые в состоянии `Анализ завершен`
- **Метод:** `GET /skinScan/photos`
- **Заголовок:** `Authorization: Bearer <AccessToken>`
- **Ответ:** `200 OK` с ответом: 
  - `id` - id фото
  - `status` - статус фото
  - `links` - подписанная ссылка на фото
  - `size_file` - размер файла
  - `processing_time` - время обработки.
- **Ошибки:**
    - `401 Unauthorized` — Необходима аутентификация, неверный или истекший токен.
- В теле ответа формируется подписанная ссылка, если MinIO и директория на хранилище фотографии если локальное хранение

### 5.10 Получение фотографии по имени
- **Метод:** `GET /skinScan/photos/name/{nameFile}`
- **Заголовок:** `Authorization: Bearer <AccessToken>`
- **Ответ:** `200 OK` с ответом:

    - `403 Forbidden` — Нет доступа к этой фотографии.
    - `502 Bad Gateway` — Фотография находится не в статусе: анализ завершен.
    - `409 Not Found` — Фотография не найдена.
- В теле ответа формируется подписанная ссылка, если MinIO и директория на хранилище фотографии если локальное хранение

### 5.12 Информация о пользователе

## 6. Миграции базы данных (Liquibase)

Все изменения схемы БД управляются через Liquibase. Файлы миграций лежат в `src/main/resources/db/migration/`.

- **Файл `V1__create_users_table.sql`** — создает таблицу users.
- **Файл `V2__create_photo_table.sql`** — создает таблицу photo.
- **Файл `V3__create_analysis_table.sql`** — создает таблицу analysis.
- **Файл `V4__aad_index.sql`** — создает индексы для быстрого доступа к определенным данным из БД.
- **Файл `V5__create_user_roles_table.sql`** — создает таблицу user_roles.

При запуске приложения с профилем `local` миграции применяются автоматически. Если БД пуста, таблицы создадутся при первом запуске.

## Асинхронная обработка
Пул потоков: Настроен ThreadPoolTaskExecutor с параметрами:
- corePoolSize = 2 — минимальное количество потоков, всегда готовых к работе. 
- maxPoolSize = 5 — максимальное количество параллельных анализов. 
- queueCapacity = 20 — задачи, ожидающие выполнения при перегрузке. 
- Превышение queueCapacity приводит к отклонению задач (возвращается ошибка 503 Service Unavailable с предложением повторить позже). 

**Жизненный цикл анализа (через @Async):**
- Контроллер получает файл, валидирует его и создаёт запись Photo со статусом UPLOADED. 
- Вызывается метод AnalysisService.processPhotoAsync(photoId), помеченный @Async. 
- Метод выполняет в фоновом потоке:
  - Сохранение файла через FileStorageService. 
  - Обновление статуса Photo → PROCESSING. 
  - Создание записи Analysis со статусом PENDING. 
  - Вызов MlService.analyze(filePath), который пока возвращает мок-данные через 3-5 секунд. 
  - Обновление Analysis (статус → COMPLETED, заполнение result_json). 
  - Обновление Photo.status → ANALYZED. 
- Если на любом шаге возникает исключение, статус переводится в FAILED, а ошибка логируется и сохраняется в analysis.error_message. 
- Обработка падений: Если сервер перезапускается во время выполнения @Async-задачи, задача теряется (это ограничение текущей реализации). В следующем спринте планируется переход на RabbitMQ для обеспечения надёжности.

## 7. Известные ограничения и технический долг

На данном этапе существуют следующие ограничения, которые будут устранены в следующих спринтах:

1. **Хранение JWT в памяти:** Токены не сохраняются в Redis, поэтому при перезапуске сервера все сессии сбрасываются.
2. **Отображение результата:** Подготовлено, но необходимо понимать как поля будут в результате анализа.
3. **Отсутствие логики восстановления доступа:** Будет добавлено позже.
