# Skin Scan — Backend

## 1. О проекте

**Краткое описание:**  
Серверная часть приложения для скрининга кожи с использованием компьютерного зрения. 
На текущий момент реализован базовый каркас системы: 
аутентификация пользователей, управление сессиями через JWT, хранение учётных записей в PostgreSQL и система централизованной обработки ошибок. Ядро продукта — загрузка и анализ фотографий родинок — находится в активной разработке.

**Текущий статус:**
- ✅ Регистрация новых пользователей с хэшированием паролей (BCrypt).
- ✅ JWT-аутентификация (пока не полноценная, без токенов с использованием Base Auth).
- ✅ Глобальный обработчик исключений с единым форматом ошибок.
- ✅ Эндпоинт `/check-run` с проверкой связности с БД.
- ✅ Эндпоинты регистрации, авторизации и изменения данных пользователя.
- ✅ Ограничение на кол-во авторизаций и регистраций с одного IP
- ✅ Миграционная схема для таблиц `users` (Liquibase).
- ✅ Многопрофильная конфигурация (local, dev, prod).
- ⚠️ Загрузка фотографий — в разработке.
- ⚠️ ML-интеграция — заглушка, реальная модель не подключена.

## 2. Стек технологий

**Описание выбранных решений с обоснованием:**

- **Язык:** Java 21.
- **Фреймворк:** Spring Boot 3.x. Используется как стандарт де-факто для RESTful сервисов; предоставляет встроенный контейнер сервлетов (Tomcat) и гибкую систему конфигурации.
- **База данных:** PostgreSQL 18+. Реляционная СУБД выбрана для гарантированной целостности данных (внешние ключи, транзакции) и поддержки JSONB-полей, которые понадобятся для хранения результатов ML-анализов.
- **Миграции:** Liquibase. Позволяет версионировать изменения схемы БД.
- **Безопасность:** Spring Security + JWT. Токены хранятся в памяти сервера (без Redis) на данный момент, что допустимо для MVP.
- **Сборка:** Gradle (Kotlin).
- **Документация API:** OpenAPI 3 (Swagger) с автоматической генерацией через Springdoc. Доступна по адресу `/swagger-ui.html`или по эндпоинту `/docs`.

## 4. Настройка и запуск (локальная разработка)

### 4.1 Клонирование репозитория
```bash
git clone <url-репозитория>
```

### 4.2 Настройка базы данных
Создайте базу данных в PostgreSQL:
```sql
CREATE DATABASE skinScan_db;
CREATE USER skinScan_user WITH PASSWORD 'your_strong_password';
GRANT ALL PRIVILEGES ON DATABASE skinScan_db TO skinScan_user;
```

### 4.3 Конфигурация приложения

Приложение автоматически использует **профиль `local`**
### 4.4 Запуск приложения
Через Gradle:
```bash
./gradlew bootRun
```
После запуска сервер будет доступен по адресу: `http://localhost:8080`.

**Проверка успешности:**
- Запрос `GET /skinScan/check-run` должен вернуть статус, время запроса, текущее время и запуска приложения.
- Swagger-документация доступна: `http://localhost:8080/swagger-ui.html`.

## 5. API Документация (Текущие эндпоинты)

Все эндпоинты документированы через OpenAPI. Интерактивная документация доступна после запуска по адресу `/swagger-ui.html`. Ниже описаны ключевые эндпоинты.

### 5.1 Регистрация пользователя
- **Метод:** `POST /skinScan/register`
- **Тело запроса (JSON):**
    - `login` (string, обязательное).
    - `password` (string, обязательное) — минимум 6 символов.
    - `email` (string) — должен быть корректным email-адресом.
    - `phone` (string).
- **Успешный ответ:** `201 Created` с телом:
    - `userId` (UUID) — идентификатор созданного пользователя.
- **Ошибки:**
    - `400 Bad Request` — невалидный email или пароль.
    - `409 Conflict` — пользователь с таким email уже существует.

### 5.2 Аутентификация (Логин)
- **Метод:** `POST /skinScan/login`
- **Тело запроса:** `login:password` в формате Base64.
- **Успешный ответ:** `200 OK` с телом:
    - `UUID` пользователя.
- **Ошибки:** `401 Unauthorized` — неверные учётные данные.

### 5.3 Проверка состояния сервера
- **Метод:** `GET /skinScan/check-run`
- **Ответ:** `200 OK` с JSON:
    - `статус` — `Успешно` или `Ошибка`.
    - `БД` — `Postgres`.
    - `Результат работы БД` — `1` если успешно или `0` если ошибка соединения с БД.
    - `Время запроса, мс` — время выполнения запроса в мс.
    - `Текущее время`.
    - `Время старта приложения`.

### 5.4 Обновление данных пользователя
- **Метод:** `PUT /skinScan/user/update`
- **Заголовок:** `Authorization: Basic Auth <логин:пароль>`
- **Тело запроса (JSON):**
  - `login` (string, обязательное).
  - `password` (string, обязательное) — минимум 6 символов.
  - `email` (string) — должен быть корректным email-адресом.
  - `phone` (string).
- **Ответ:** `201 OK` с полем: `id`.
- **Ошибки:**
  - `400 Bad Request` — невалидный email или логин.
  - `401 Unauthorized` — неверный пароль.

### 5.5 Смена пароля пользователя
- **Метод:** `PUT /skinScan/user/update/{login}`
- **Заголовок:** `Authorization: Basic Auth <логин:пароль>`
- **Тело запроса (JSON):**
  - `newPassword` (string, обязательное).
  - `oldPassword` (string, обязательное).
- **Ответ:** `201 OK` с полем: `id`.
- **Ошибки:**
  - `400 Bad Request` — невалидный новый пароль.
  - `401 Unauthorized` — неверный логин или старый пароль.

## 6. Миграции базы данных (Liquibase)

Все изменения схемы БД управляются через Liquibase. Файлы миграций лежат в `src/main/resources/db/migration/`.

- **Файл `V1__create_users_table.sql`** — создает таблицу users.

При запуске приложения с профилем `local` миграции применяются автоматически. Если БД пуста, таблицы создадутся при первом запуске.

## 7. Известные ограничения и технический долг

На данном этапе существуют следующие ограничения, которые будут устранены в следующих спринтах:

1. **Хранение JWT в памяти:** Токены не сохраняются в Redis, поэтому при перезапуске сервера все сессии сбрасываются.
2. **Загрузка файлов:** Отсутствует полностью (эндпоинты для фото не реализованы).
3. **Отсутствие логики восстановления доступа:** Будет добавлено позже.

## 8. План развития (Roadmap)

- **В разработке:**
    - Реализация загрузки и хранения фотографий (локальное хранилище + MinIO).
    - Асинхронная обработка изображений через `@Async`.
    - Создание сущностей `Photo` и `Analysis` + миграции. (`Photo` будет иметь поля:
      - id, 
      - user_id (внешний ключ к таблице users), 
      - original_filename (имя, которое дал пользователь), 
      - storage_path (внутренний путь/ключ в хранилище), 
      - file_size_bytes (число) — для статистики и проверки лимитов, 
      - mime_type — для валидации и корректной отдачи, 
      - uploaded_at — момент загрузки,
      - status — жизненный цикл: UPLOADED, PROCESSING, ANALYZED, ERROR.)
    
      (`Analysis` будет иметь поля: 
      - id,
      - photo_id (внешний ключ к photos),
      - status (enum: PENDING, IN_PROGRESS, COMPLETED, FAILED),
      - result_json — поле типа JSONB в PostgreSQL,
      - confidence_score (число с плавающей точкой),
      - requested_at (когда анализ был запущен),
      - completed_at (когда получен ответ от ML),
      - error_message — если анализ упал, сохраняем причину для отладки.)
    - Интеграция с ML-заглушкой и разработка эндпоинта для получения статуса.
- **Будущий:**
    - Подключение реальной ML-модели (вместе с ML-инженером).
    - Добавление пагинации и фильтрации для истории анализов.
    - Реализация отправки уведомлений о завершении анализа (WebSocket / Push).
    - Настройка мониторинга (Prometheus + Micrometer).
    - Внедрение Redis для кэширования результатов.
    - Написание E2E-тестов с использованием Cucumber.
